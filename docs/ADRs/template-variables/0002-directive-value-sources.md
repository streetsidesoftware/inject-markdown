# ADR-0002: Directive-level value sources and opt-in trigger

**Status:** Accepted
**Date:** 2026-09-21
**Deciders:** Jason Dent

## Context

With the placeholder grammar decided ([ADR-0001](0001-placeholder-syntax.md)), a directive needs a way to supply the values it looks up: inline, for a handful of literal values, or from a file, for many values (e.g. generated by CI from `package.json`). The feature request itself proposed both `#value:name=project` (inline) and `#values-file=../values.json` (file).

We also need to decide when a directive's content is even scanned for placeholders at all. Scanning unconditionally would warn about `{@ ... @}` text in any directive that happens to contain it without intending to use this feature — including this tool's own generated docs demonstrating the syntax.

## Decision

1. **Inline values — `values=name:val,name2:val2`.** One hash-option key holding comma-separated `name:value` pairs, consistent with the list/map-valued-option convention from [table-improvements ADR-0001](../table-improvements/0001-table-option-encoding-conventions.md) point 2 (`columns=Name,Age:,Price:` over repeated keys). The whole value may be wrapped in double quotes to permit literal commas/colons inside a value (`values="name:1, 2, 3"`), mirroring `columns`'s whole-value quoting for spaces ([table-improvements ADR-0001](../table-improvements/0001-table-option-encoding-conventions.md) point 3).
2. **File values — `values-file=[prefix:]path[,[prefix:]path...]`.** One or more JSON files (JSON-only for this feature; see Consequences). By default each file is namespaced under a prefix auto-derived from its own basename (`values-file=package.json,shared.json` → `package.*`, `shared.*`); an explicit prefix overrides that (`values-file=pkg:package.json`); a leading colon with no prefix (`values-file=:package.json`) merges that file's keys directly into the root namespace instead. See [ADR-0007](0007-values-file-prefixing.md) for the full syntax and collision rule. Each path is resolved relative to the Markdown document containing the directive — the same rule already used for a directive's own injected-file reference (`dFile.toUrl(fileUrl)` in [FileInjector.ts](../../../src/FileInjector/FileInjector.ts)). Every path is a local file read and is therefore subject to the same injection-root boundary as any directive file reference ([file-access-security ADR-0001](../file-access-security/0001-injection-root-boundary.md)/[ADR-0002](../file-access-security/0002-injection-root-escape-hatch.md)): resolved and realpath-checked before being read, respecting `--allow-outside-root`.
3. **Bare opt-in flag — `#vars`.** A directive with no inline `values=`, `values-file=` or `value-alias=` ([ADR-0010](0010-value-alias.md)) of its own can still opt into placeholder scanning — to use CLI-wide/environment sources alone ([ADR-0003](0003-cli-and-env-value-sources.md)) — by adding the bare flag `#vars`, following the bare/flag-option precedent `header-rows` set in [table-improvements ADR-0002](../table-improvements/0002-table-header-rows-option.md).
4. **Opt-in rule.** A directive scans its injected content for placeholders — and only then warns/errors about unresolved ones — if it carries at least one of `values=`, `values-file=`, or `#vars`. A directive with none of these does no scanning: `{@ ... @}` text in its content passes through untouched and silently.

## Options Considered

- **`values-file=` limited to a single path** — the original decision here — reversed once it became clear a directive commonly wants to combine values from more than one source file (e.g. `package.json` for `version` plus a separate CI-generated `build-info.json`), which a single-path option can't express. Superseded by the list-with-optional-prefix syntax in [ADR-0007](0007-values-file-prefixing.md).
- **Repeated-key `value:name=val` per name** (the request's own suggested syntax) — rejected in favor of `values=name:val,...`: matches the existing comma-separated-list convention instead of introducing a new distinct-repeated-key pattern that `parseHashString`'s current repeated-key handling (accumulate same key into one array) doesn't support.
- **Always-on scanning, no opt-in** — rejected: produces false-positive unresolved-placeholder warnings on any directive whose content happens to contain `{@ ... @}` without meaning to use this feature.
- **`values-file=` exempt from the injection-root boundary** — rejected: it is still a local file read triggered by directive text in a processed Markdown file, exactly the exposure [file-access-security ADR-0001](../file-access-security/0001-injection-root-boundary.md) closes; no principled reason to carve out an exception for it.

## Consequences

- `parseHashString` ([hash.ts](../../../src/util/hash.ts)) gains two new keys (`values`, `values-file`) and one new bare-flag tag (`vars`) — no new parsing layer, same machinery as existing options. [ADR-0010](0010-value-alias.md) adds a third key, `value-alias`, which also opts a directive in.
- Once the injection-root check from [file-access-security ADR-0001](../file-access-security/0001-injection-root-boundary.md) lands, it needs to be reachable from wherever `values-file=` is read, not just the three existing call sites (`readAndParseMarkdownFile`/`-CodeFile`/`-TableFile`) that read a directive's main file.
- JSON-only for v1: there is no YAML-parsing dependency in this project today (`remark-frontmatter` delimits YAML frontmatter but doesn't parse it), so supporting `.yaml` values files is deferred to a follow-up ADR if it turns out to matter.
- New glossary terms: **`values=` option**, **`values-file=` option**, **`vars` flag**. See also [ADR-0007](0007-values-file-prefixing.md) for **Values-file prefix**.
